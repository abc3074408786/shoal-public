Velella execution sandbox — runtime and task integration

Status
The Linux Restricted tool backend is connected to the original desktop Codex
terminal and retains its native TUI/PTY. It is an opt-in experimental Git-worktree
mode using Landlock/seccomp, separate from the namespace-based Isolated mode.
The current implementation provides trusted system tools and recovery of the
same model thread after a confirmed normal stop. See "Current native terminal:
tools and same-thread recovery" at the end for the current scope and evidence.
The earlier chat-panel, startup-only and no-recovery sections below are historical
stages; the separate Restricted chat-panel adapter still has no recovery support.

The shared PTY execution entry point accepts an explicit sandbox policy. Old
requests/descriptors default to native and keep their original behavior. The Linux
backend uses /usr/bin/bwrap. Windows and macOS isolated backends are unimplemented
and reject isolated requests. This is not a container/VM implementation.

Entrypoints
  velella session sandbox-capabilities
  velella-runtime sandbox-capabilities
Both commands probe locally without needing a daemon. Existing daemon protocols
also accept {"cmd":"sandbox.capabilities"}.

With a running CLI daemon, opt into isolation for a new session:
  velella session spawn --cwd /absolute/canonical/task-directory \
    --sandbox-policy examples/sandbox-isolated.json -- /bin/sh
The daemon's session.spawn JSON accepts the same object in its "sandbox" field.
Native policy is {"mode":"native"}. Isolated policy is:
  {"mode":"isolated","read_only":[],"writable":[],"network":"denied"}
Unknown fields, modes and network modes are rejected. Additional mount paths must
be absolute, canonical, existing directories; overlaps and reserved paths fail.
The cwd itself is writable and must not be repeated in writable/read_only.

Isolation contract
The host root and HOME are not mounted. System executable/library directories and
selected loader/TLS files are read-only. The working directory and explicitly
listed writable directories are writable. /tmp is private and ephemeral. HOME is
ephemeral unless a dedicated home directory is explicitly configured; task HOME
is managed and persistent across setup, agent, verification, shells and recovery. Host environment variables are cleared.
Only explicit request env plus safe PATH/terminal defaults enter the sandbox;
HOME and TMPDIR cannot be overridden. User/IPC/PID/UTS namespaces are isolated,
capabilities dropped, and a new terminal session prevents controlling-terminal
injection. Bubblewrap manages child reaping and die-with-parent cleanup.

network=denied creates a private network namespace. network=host explicitly gives
full host networking, including localhost and the local network; it is NOT a domain
allowlist. Filesystem access and network policy are separate controls.

Capability detection executes the actual namespace/mount setup with /bin/true,
not just a binary/version check, with a three-second timeout. An installed bwrap
can still be unusable under host/container security policy. Isolated execution
fails closed, including when mounts fail after the probe. It never retries the
requested command natively. No host security setting is changed by the probe.

Task execution
Desktop task definitions accept policy.execution with the same schema. See
examples/task-isolated.yaml. Creation and preparation probe the backend and reject
unavailable isolation before creating a worktree or running setup. All task phases
use the same policy, including retries, verification and the task's manual shell.
Policy survives task YAML export and persisted task JSON. Legacy definitions stay
native. Direct-folder tasks are not supported in isolated mode. The older CLI task
runner explicitly rejects isolated tasks; use the desktop runtime task executor.

Task HOME is created under <data-dir>/sandbox-tasks/<task-id>/home, mounted at
/home/velella. Omit execution.home for tasks. No existing host account/config/keyring
is imported. Sign in through the task terminal if needed. Tools installed outside
the standard system directories require explicit canonical read_only installation
directories, including their interpreter/runtime dependencies. Agent executable
resolution fails explicitly when its installation is not visible to the sandbox.
Read-only Git common metadata is mounted automatically for status/diff; commits
and index writes remain unavailable. GIT_OPTIONAL_LOCKS=0 avoids optional writes.

Agent sessions receive a dedicated read-only support directory containing settings
and an event-only Unix socket. A task-scoped copy of the runtime implements the
hook client. That socket accepts only known hook events and bounded metadata;
terminal input, kill, resize, permission changes and arbitrary RPC are rejected.
Setup/check/shell sessions get no hook socket. The full host control socket and
runtime data root are never mounted automatically; explicit task mounts exposing
the runtime data root are rejected. Hook events remain agent-reported telemetry,
not proof of correctness: configured verification commands still determine checks.

Browser/MCP injection is disabled for isolated tasks pending a scoped browser
broker. Native chat still rejects isolated descriptors. Existing Codex/Claude
native permission flags remain in place inside the outer sandbox. Credentials and
session data in task HOME persist for recovery; automatic cleanup is not yet
implemented. The desktop new-task dialog offers execution mode, network access
and optional read-only/writable directories. Capability checks disable unavailable
isolation; a failed recheck never changes an isolated selection to native. Task
details show the saved execution scope. YAML and task.create remain supported.

Scope and outstanding work
Windows/macOS backends, scoped browser brokering, and real authenticated Agent
end-to-end validation remain outstanding. Kernel isolation acceptance passed on
a GitHub-hosted Ubuntu 22.04 runner on 2026-10-20 (details below). A successful descriptor/bridge test is
not a claim that a real Agent completed a task inside the kernel sandbox.

Policies and mount roots are trusted host inputs. Mounting sensitive directories,
Unix sockets or runtime state can grant host capabilities. Use dedicated task
directories, not the user's home, application runtime directories or Docker socket
locations. This first backend has no syscall filter, CPU/memory/disk quotas,
credential broker, network proxy or VM boundary. It is not yet approved for
hostile multi-tenant workloads. Explicit env values are launch metadata; do not
use them as a secret store. Host-mounted data remains accessible to the host.

Strict acceptance runner
  python3 scripts/verify-sandbox.py
Writes logs and result.json to artifacts/sandbox-acceptance (or --output). Exit 0
means the kernel, task-policy and hook-bridge checks passed. Exit 2 means the host
cannot support the required sandbox; exit 1 means a build/probe/test failed. The
script does not change host security settings or start an authenticated Agent.
It also runs a deterministic test Agent through the real runtime: Git worktree
preparation, setup, PTY launch, event-only hooks, verification, review and resume.
This is explicitly distinct from a real Claude/Codex model completing a task.
The test is ignored in ordinary unit runs because it requires a built runtime and
working namespaces. To invoke it directly on a prepared Linux host:
  cargo build -p velella --bin velella-runtime
  VELELLA_REQUIRE_SANDBOX=1 VELELLA_TEST_RUNTIME="$PWD/target/debug/velella-runtime" \
    cargo test -p velella --lib live_task_pipeline_with_fixture_agent -- --ignored --nocapture
The receipt includes a fixed allowlist of host diagnostics: kernel version,
namespace limits, AppArmor userns restriction/profile, and required executable
availability. These values are evidence, not proof of which security rule denied
the mount. No environment variables or credentials are collected. Cargo metadata
locates the runtime binary even when a custom target directory is configured.
Test the runner's pass/fail/blocked/timeout handling without launching a sandbox:
  python3 scripts/test-verify-sandbox.py
The manual sandbox-acceptance GitHub workflow requires a prepared self-hosted
Linux runner labelled velella-sandbox with Rust, system build dependencies,
/usr/bin/bwrap and /usr/bin/python3. It uploads the receipt even on failure.

Experimental local restricted task backend — 2026-10-20
The filesystem prototype above is historical. A separate runtime execution
mode now connects Landlock and seccomp to the task runtime:
  {"mode":"restricted","network":"denied","read_only":[],"writable":[]}
See examples/sandbox-restricted.json. The task runtime supplies a private HOME.
Native remains the default. Restricted is distinct from the Bubblewrap isolated
mode, never an automatic fallback when Bubblewrap fails. Unsupported platforms,
missing kernel support and invalid policies refuse execution.

On this development machine, actual runtime capability probes report Bubblewrap
unavailable (/proc mounting denied), but restricted available. The latter probe
runs in a fresh process, installs both policies, checks allowed runtime reads and
denied outside reads/INET/INET6/external UNIX sockets, and requires an exact receipt.
The parent daemon is never restricted by the capability check.

Restricted uses Landlock ABI >= 3, no_new_privs, dropped capabilities, a clean
environment and task-owned HOME/.tmp. Only approved directories, system runtime
files and specific devices are accessible. The launcher closes inherited FDs >= 3
and rejects sockets, regular files and directories as standard descriptors.
Seccomp denies network and external UNIX sockets, io_uring, process-control alternatives,
namespace operations and metadata mutation. Architecture/x32 checks and argument
checks for clone, ioctl and fcntl prevent the tested alternate paths.
Anonymous AF_UNIX/SOCK_STREAM and SOCK_SEQPACKET socket pairs with protocol 0
are permitted for communication within the task. STREAM supports the real Codex
CLI's signal handling; SEQPACKET supports anonymous packet IPC. Only CLOEXEC and
NONBLOCK flags are accepted. Other pair domains/types/protocols/flags and
connect/bind/listen/accept/sendmsg/recvmsg remain denied.

Setup, Agent, verification and task shell all preserve the selected policy.
The event-only hook transport uses a separate writable inbox, since a UNIX socket
would violate the network policy. The host pins the directory FD before launch,
accepts bounded regular single-link files, filters the event schema, and sends
atomic acknowledgements in order. Agent-accessible helpers/settings are read-only;
the daemon control endpoint, user login files and unrelated runtime state are
outside the permitted directories.

This mode is experimental, Linux-only and offline. There is no PID/mount namespace,
metadata hiding, resource quota, credential broker or model network transport.
Even writable directories cannot use chmod/chown/utime/xattr updates, so some
installers and developer tools will fail. Existing hard links inside permitted
directories and hostile host-side replacement of policy directories are outside
the demonstrated guarantee; only grant directories appropriate for the task.
The UI explicitly explains these limits and cannot select host networking for
Restricted. No authenticated model test is implied by fixed-fixture acceptance.

Lifecycle handling uses a private PTY process group. Restricted descendants cannot
call setsid/setpgid; cancellation kills the whole group. Normal leader exit also
terminates remaining descendants. waitid(WNOWAIT) retains the leader PID until
group cleanup finishes, preventing later cancellation from targeting a reused PID.
Real host/PTY tests cover cancellation and natural exit with children/grandchildren
that ignore SIGHUP. Abrupt loss of the host process is not covered by this cleanup
guarantee; this backend does not have a cgroup or independent lifecycle guardian.

The intended integration uses a trusted controller-side protocol adapter that
launches each command and filesystem operation through restricted-exec. The
adapter owns process groups outside the filter; each actual task operation runs
inside the existing kernel restrictions. This is separate from embedding the
native exec-server inside one sandbox, which is the failed experiment above.

The app-server client RPC layer must retain its explicit method allowlist:
app-server fs/readFile/fs/writeFile and process/spawn refer to host operations;
they are different from the selected environment's exec-server protocol.
include_local=false is not an access-control policy for arbitrary app-server
client RPCs. Plugins, MCP, browser/computer tools and other host-side extensions
also need separate review before enabling them in a restricted product mode.

hash, history_ready and shell-history status. Only an admitted native thread/start or
thread/resume success establishes a binding. Before resume, only a metadata
lookup of that exact ID is permitted; execution is admitted only after the
native resume succeeds. Arbitrary history/path imports, cross-thread requests,
forking and client-supplied configuration or permission overrides stay blocked.

Recovery reuses only byte-matching fixed controller config, environment registry,
executor configuration and embedded scripts. Local execution remains absent:
include_local=false and the default environment are fixed, and every subsequent
model turn explicitly selects velella-restricted. The original ChatGPT account
hash is checked before private external-auth login; changing account or provider
profile cannot silently send old history through a different identity/provider.
No source auth file or refresh token is copied into the controller or tool HOME.

Manual !commands mark shell history dirty before execution. The bridge clears
that flag only after native thread/inject_items acknowledges the saved command
and result. A later model request waits for this acknowledgement. A new empty
thread starts with history_ready=false: thread/start alone does not materialize
a rollout in 0.153.4. A successful shell injection, or a model completion followed
by an acknowledged internal persistent history read, marks it ready. Empty
terminals therefore have history playback but no model recovery action. The pinned
native app-server persists even the first shell result before any model turn;
an independent no-model restart check confirms the same ID can resume and accept
further history. Recovery does not replay a pending command. A dirty checkpoint,
missing history, missing/mismatched generation, or unconfirmed cleanup refuses
recovery; SIGKILL/crash recovery is not enabled. Saved terminal bytes remain
available for historical playback even when model recovery is unavailable.

Normal stop freezes request producers, terminates the owned tool groups and
waits for both relevant adapters. Each adapter writes its own private cleanup
receipt only after its recorded processes and operations finish; PID and /proc
start-time bind that receipt to the expected adapter. Rust checks those receipts
before publishing terminal-stopped.json for the current generation. A vanished
adapter or a zero exit status alone cannot establish that tool cleanup finished.
The previous stop marker is invalidated before the next generation starts.

The host can leave a Unix endpoint after exit. Recovery first holds owner.lock;
listen_recovering then reclaims only a current-user-owned socket that no longer
accepts connections, retaining the saved descriptor/history. The bridge's
separate private socket is removed during normal cleanup. The viewer is
recreated on confirmed exit or a changed host PID, drops old input queues and
replays geometry before negotiating live resize.
Input/resize/control requests carry the viewer's expected host PID; the host
rejects stale requests rather than applying them to the recovered process.

The native TUI remains interactive, but each !command itself is non-interactive:
default timeout 120 seconds, maximum output 256 KiB and 64 executed manual
commands per shell adapter. Timeout/output-limit/cap failures remain visible
without changing the execution policy. These limits are not a general CPU,
memory or disk quota, and a tool subprocess still has no model-service network.
