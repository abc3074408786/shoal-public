Linux task-source credentials

Linux uses the logged-in user's Secret Service keyring through keyring 3.6.3
(sync-secret-service + crypto-rust). The build requires dbus-1 development files;
the running app requires libdbus and an available, unlocked Secret Service in its
session bus. A headless daemon without that session cannot save or read nonempty
source credentials. It fails explicitly; there is no plaintext fallback.

The keyring entry dev.velella.task-sources / encryption-key-v1 contains the random
256-bit key. SQLite contains only versioned AES-256-GCM ciphertext (VLSS1 header,
random 96-bit nonce, authentication tag). The file under
~/.local/share/velella-credentials/key.lock only serializes creation across
processes. It contains no key or token. Empty tokens used by CLI-authenticated
sources remain empty and do not require the keyring.

Windows retains DPAPI and its existing data format. Ciphertexts are not portable
between OS users/machines without the matching keyring key. A missing key or
invalid/corrupted ciphertext requires reconnecting the source; reading never
silently generates a replacement key. Do not delete the keyring entry while
saved task-source credentials are still needed.

Validation on 2026-10-20 uses fake tokens and local HTTP fixtures. It proves local
storage/roundtrip, rejection of tampering, no fallback when Secret Service is
unavailable, source association persistence and request idempotency. It does not
prove a live Linear/Jira/GitHub/GitLab connection. No external account was changed.
